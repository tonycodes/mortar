# Contribute

Clone https://github.com/tonycodes/mortar, run `npm ci`, `npm run check` and `npm run dev`. Use `npm run test:browser` for both-theme accessibility/rendering checks. The local playground defaults to port 4340. No service registration or npm token is required.

Run `npm run check` before regenerating anything. When you change a component, its preview or shared styles, the check fails with M007 (a source or preview fingerprint changed) or M008 (the catalogue no longer matches the manifests). Review what you changed, then run `npm run catalog`. It rewrites catalog.json and prints which components' fingerprints and contracts changed; check that list matches your intent before committing. Running `npm run catalog` first would accept any drift unseen.

Use src for central implementations, previews for fixtures and manifests for contracts. Read DESIGN.md (principles and API conventions) and TESTING.md; AGENTS.md summarises the rules for coding agents. A manifest documents every prop the component declares; `tests/manifest-props.test.mjs` compares it with the TypeScript types, and rule M010 requires `contract.dependencies` to list exactly the catalogue components the source renders. `npm run catalog` generates the prop types, capabilities derived from the test contract, provenance, version and fingerprints into catalog.json. Include a reproducible issue and a regression test for fixes. Open a PR with actual check results and visual evidence. Shared shells are versioned alongside controls; applications supply content through props.

Baseline rules are versioned in baseline-policy.json. CI must use the same rules but contributors cannot authorize weakening protected checks; policy, workflow and dependency changes require maintainer review. Branch protection requires successful checks. The solo maintainer reviews and authorizes merges; a second GitHub approval is not required. Public PR runners must be isolated from release credentials and production networks.

Releases are automatic and version-driven. To release, merge a PR that bumps the version with `npm version <x.y.z> --no-git-tag-version`. `npm run check` then fails with M008 until `npm run catalog` stamps the new version onto every catalogue entry (tests/versioning.test.mjs enforces they match). The same PR renames CHANGELOG.md's `## Unreleased` section to `## <x.y.z> (<date>)`. That section becomes the GitHub release notes; a test requires it, and a release without one stops before tagging. Breaking changes before 1.0 also get a migration guide in docs/, such as [Migrating to 0.6](docs/migrating-to-0.6.md). After the required checks pass on that merge commit, the Release package workflow (.github/workflows/release.yml) acts only if the version is neither tagged on another commit nor already on npmjs.com. Its credential-free prepare job builds the exact commit with npm run release:prepare and checks the provenance record. Its publish job runs in the protected npm-release environment and never checks out or runs repository code. It holds no registry secret: it authenticates with npm trusted publishing, exchanging a short-lived GitHub OIDC token (`id-token: write`) for a short-lived publish credential, and only a job in this repository, workflow file and environment can do that. It re-verifies the archive and creates the immutable v<version> tag on that commit. It then creates the GitHub release with the archive and provenance.json, publishes that exact archive to npmjs.com with `npm publish --provenance`, and confirms (allowing for registry propagation) that npmjs.com serves the integrity recorded in the provenance. The provenance attestation on npmjs.com links the version to the workflow run that built it. Merges that do not change the version publish nothing. A version is never overwritten: an existing tag on another commit stops the release, and a rerun publishes the archive already attached to the GitHub release. Prerelease versions such as 1.0.0-rc.1 are published under the next dist-tag. The maintainer's merge of the version bump is the release authorization; agents must not open or merge version bumps on their own initiative.

Versions up to 0.11 were published to the previous owner-hosted registry (see the CHANGELOG.md migration note); new releases go to npmjs.com.

### Maintainer setup

This is one-time configuration in npmjs.com and the GitHub repository settings; no secret is created.

1. On npmjs.com, create the `tony-ui` organisation (the `@tony-ui` scope), or confirm it exists and that you own it.
2. Add a trusted publisher to the `@tony-ui/mortar` package (package settings, Trusted publisher, GitHub Actions): organisation or user `tonycodes`, repository `mortar`, workflow filename `release.yml`, environment `npm-release`. A trusted publisher is configured on an existing package. If `@tony-ui/mortar` is not on npmjs.com yet, bootstrap it from a maintainer machine (with 2FA) using the already-released, provenance-checked 0.11.0 archive, so npmjs.com matches the GitHub release byte for byte: `gh release download v0.11.0 --repo tonycodes/mortar -p tony-ui-mortar-0.11.0.tgz`, then `npm publish ./tony-ui-mortar-0.11.0.tgz --registry https://registry.npmjs.org/ --access public`. Then add the trusted publisher, and under the package's publishing access choose "Require two-factor authentication and disallow tokens".
3. In GitHub, keep the `npm-release` environment restricted to `main` (and optionally add yourself as a required reviewer).
4. In GitHub Settings › Pages, set the source to "GitHub Actions". The `github-pages` environment is created on first deployment; keep it restricted to `main`.
5. Optional custom domain: set it in Settings › Pages (with an Actions deployment the setting, not a `CNAME` file, is what counts) and add the DNS record GitHub shows. The playground is built with a relative base, so it works at any path without a rebuild; then update `homepage` in package.json, the links in README.md, site/index.html and tests/domain.test.mjs.
6. After the first npmjs.com release, deprecate and retire the previous owner-hosted registry and the old playground/cloud server, then delete the now-unused GitHub secrets `MORTAR_REGISTRY_TOKEN` and `PLAYGROUND_DEPLOY_KEY`, the variables `PLAYGROUND_DEPLOY_HOST` and `PLAYGROUND_KNOWN_HOSTS`, and the `playground-production` environment.

## Pull request review

GitHub is the component review authority. Include the evidence in the PR template. CI uploads a runnable `mortar-playground-<commit>` artifact and a browser report with screenshots for both themes. Download and extract the playground, run `python3 -m http.server 4340 --bind 127.0.0.1` in that directory, and open http://127.0.0.1:4340. No package install or account is needed for this preview. Use an isolated browser profile for untrusted PR code. Never deploy PR artifacts to the production site.

Preview artifacts are review evidence, not approved releases. GitHub maintainer review and successful required checks apply to the current PR commit. Source changes invalidate prior approval. A merged change needs a new immutable package version before consumers adopt it. There is no other approval step.

## Contributor identity

Use a contributor identity or dedicated GitHub App where available. Do not give contributors package-publishing or repository-administration credentials. For this solo-maintainer repository, passing required CI and the owner's explicit merge authorization are the review gate; no second GitHub reviewer is required. Agents must not self-authorize a merge or release.

## Executable test contract

See [TESTING.md](TESTING.md) for profiles, state fixtures, integrity checks, execution reports and visual baselines. Run both `npm run test:browser` and `npm run test:visual`; catalogue presence or an axe pass on playground chrome is not sufficient. Baseline images and changes to the test policy require maintainer review in the PR.

## Browsing the playground

The playground opens on an overview of the five kits: Foundation, Application, Marketing, Docs and Ecommerce (`playground/taxonomy.json`). Each kit is split into categories (for example Foundation › Form controls), shown as cards with a live, inert thumbnail and a component count. A category page lists every component in it as a framed example; a component page adds breadcrumbs, preview settings and previous/next links. Every example has a Preview/Code switch, and the Code view shows the JSX the preview renders, extracted from the fixture source with the TypeScript parser (`playground/examples.mjs`; `tests/playground-code.test.mjs` checks every component). Categories live in `playground/taxonomy.json`; `tests/playground.test.mjs` fails if a component is missing from it or listed twice, so add new components there.

Search by component, kit or category name. On narrow screens, Menu opens the same catalogue. Kit, category, component, brand, density, appearance, declared example states and the Code view are reflected in the URL, so a page can be shared or revisited. Open “Usage and component contract” for imports and prop metadata. The explorer composes the shared DocsShell with its `wide` layout; shell fixes belong in the kit, not playground CSS.

## Automatic playground deployment

Merges to `main` automatically deploy the GitHub Pages site at https://tonycodes.github.io/mortar/, with the playground at https://tonycodes.github.io/mortar/playground/, after the required checks pass on the merged commit. On a push to `main`, the checks workflow builds the site with no deployment credential: `site/index.html` at the root and the playground under `playground/`, built with a relative base (`--base ./`) so it also works on a custom domain. The separate Deploy playground workflow (.github/workflows/deploy-playground.yml) downloads that exact artifact, skips superseded commits, and deploys it with `actions/deploy-pages` in the `github-pages` environment; it never checks out or runs repository code. Failed checks leave the current site unchanged. This does not publish a package; only a merged version bump does (see above).
